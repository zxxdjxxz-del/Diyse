## 1. Scope and Canon Status

v0.09D adds persistence and restoration to the device-tested v0.09C field foundation. It does not redesign the gatehouse route, movement, cameras, art, combat, Cards, progression, or narrative content.

Implementation-authoritative scope:

- save schema 5;
- migration from valid schema-4 saves;
- active-field persistence;
- validated authored safe-spawn persistence;
- Crest bridge activation persistence;
- summit shortcut persistence;
- gatehouse completion persistence;
- field-aware return after battle and menus;
- safe restoration after app suspension or closure;
- corruption and non-finite-value rejection;
- New Game reset behavior;
- unchanged permanent save namespace and signing certificate.

The old Yahtrean gatehouse’s final placement, architecture, history, encounters, rewards, dialogue, and story function remain provisional unless separately approved in the Active Master Canon.

## 2. Location Identity and Three Visible Time Layers

v0.09D does not change the identity established by v0.09B and v0.09C:

- **Original function:** defended Yahtrean passage controlled by surviving Crest machinery.
- **Transformation:** damage and Ruin exposure disconnect routes and create unsafe circulation.
- **Current adaptation:** Cyanis restores bridge access, crosses the hazard route, and opens a summit shortcut.

Persistence ensures these spatial changes remain true after Continue instead of silently resetting the location.

## 3. VII–X Source Trace

### FFVII

- changed map connectivity remains understandable and consistent after returning;
- shortcuts preserve solved traversal and reduce repetition;
- restoration never places the actor inside a hazard or invalid overlapping route;
- explicit safe points protect authored traversal from arbitrary-coordinate errors.

### FFVIII

- a facility’s operational state persists because the mechanism is part of how the architecture functions;
- bridge activation and shortcut access are treated as durable system state rather than temporary presentation;
- field-aware return preserves the current operation instead of redirecting every activity to an unrelated map.

### FFIX

- compact connected compositions retain their changed circulation and route meaning after interruption;
- field return respects the active character circumstance and current location;
- the player resumes in a compositionally readable safe location.

### FFX

- progress along a directed route persists without forcing repeated solved traversal;
- safe restoration supports clear critical-path continuity;
- late or changed route states remain part of the location’s current adaptation.

## 4. Persistence Model

### Field identity

The save stores one validated field identifier:

- `gatehouse`;
- `courtyard`.

Unknown or empty field IDs normalize to the gatehouse safe start.

### Safe spawn identity

The save stores authored anchor IDs rather than arbitrary gatehouse X/Y coordinates. Approved gatehouse anchors include:

- approach;
- stair court;
- lower arch;
- mechanism chamber;
- upper landing;
- bridge exit;
- pulse safe pockets one through three;
- summit.

The courtyard retains sanitized legacy coordinates because its existing free-movement save behavior is already established. Non-finite or extreme values fall back to the courtyard’s safe start.

### Durable gatehouse flags

- bridge active;
- shortcut unlocked;
- gatehouse completed.

Completion implies shortcut access, and shortcut access implies bridge activation.

### Transient state excluded from saving

The following are reconstructed rather than persisted:

- held touch input;
- acceleration velocity;
- camera-basis blend progress;
- transition fade progress;
- Ruin-pulse animation phase;
- temporary knockback;
- battle-only state;
- menu selection;
- foreground fade interpolation.

---

## 5. Safe Restoration Rules

1. The saved field ID is normalized.
2. Gatehouse mechanism flags are normalized before map construction.
3. The requested gatehouse spawn is looked up in the authored resume catalog.
4. An upper-route anchor that requires an inactive bridge falls back to the mechanism chamber.
5. A pulse-corridor resume always resolves to a safe pocket or safe route anchor, never the active hazard lane.
6. The matching camera is selected before player control begins.
7. Invalid, corrupted, unknown, non-finite, or out-of-bounds data falls back to a known safe start.
8. Restored movement begins with neutral input and no inherited momentum.

The accepted `GatehouseMap.java` geometry remains byte-for-byte unchanged.

---

## 6. Save and Return Events

Field state is persisted at controlled events:

- explicit Save & Title;
- application pause;
- application disposal;
- mechanism activation;
- summit shortcut activation;
- transition to courtyard after gatehouse completion;
- courtyard save;
- entry into battle or menus when current field state is known.

Continue, menu return, and victory return reopen the stored active field rather than always forcing the old courtyard.

---

## 7. Schema Migration

### Schema 4 to schema 5

A valid schema-4 save remains eligible for Continue. Existing party, objective, inventory, Card, progression, and courtyard-coordinate data are preserved.

Because schema 4 has no trustworthy gatehouse field-state keys, migration starts the gatehouse at the authored approach anchor with bridge, shortcut, and completion flags inactive.

The migrated save is written as schema 5 under the unchanged preference namespace `diyse-prototype-v001`.

### New Game

New Game clears all prior field identity, spawn anchor, bridge, shortcut, and completion progress and begins from the authored gatehouse start.

## 8. Geometry, Movement, and Visual Preservation

v0.09D must not alter:

- gatehouse surface coordinates or connections;
- camera-relative analog movement;
- acceleration or deceleration;
- wall sliding;
- stair slopes;
- elevation continuity;
- camera-basis blending;
- protected edges;
- Crest mechanism interaction zone;
- Ruin-pulse timing;
- safe-pocket geometry;
- authored v0.09C backgrounds, atmosphere, masks, bridge overlay, or Cyanis sheet;
- Cyanis-only normal field presentation;
- no-permanent-follower rule.

The persistence overlay verifies the accepted gatehouse geometry file by SHA-256 before tests run.

## 13. Acceptance Statement

When automated verification and Android device acceptance pass, v0.09D will establish the first persistence-safe Diyse field baseline.
